# BMOPF Draft Data

**An open, growing library of unbalanced distribution-network benchmarks for optimal power flow — traceable to real feeders, licensed for reuse, and ready to drop into your solver.**

Distribution systems are where the energy transition actually lands: rooftop
solar, EV chargers, batteries and heat pumps all connect to unbalanced,
multi-wire low- and medium-voltage networks. Yet for decades this is exactly
where the research community has lacked what transmission has long enjoyed — a
*common, open, well-characterised set of benchmark problems* everyone can test
against. Results are hard to reproduce, methods are hard to compare, and every
group re-invents its own test cases from scratch.

This repository is a **companion data repository** to the IEEE PES Task Force on
*Benchmarking Multiconductor OPF for Distribution Systems*. It collects draft
benchmark test cases in the **BMOPF JSON format** — the data model developed by
that Task Force for up-to-four-wire optimal power flow ([schema and report](https://github.com/frederikgeth/bmopf-report)) —
together with the raw source networks and tooling you need to build your own.

> **Think PGLib, but for four-wire, unbalanced distribution OPF.** Real
> networks, clean data, full provenance, permissive licensing.

> [!IMPORTANT]
> **These are my own draft cases, not official Task Force benchmarks.** This
> repository is maintained by Frederik Geth to *support* the Task Force effort,
> not to compete with it. The cases here are personal drafts — proposed
> candidates that the Task Force has **not** (yet) reviewed or accepted. They
> are shared openly so the community can start experimenting immediately and so
> that potential benchmarks get real-world exercise before formal adoption.
> When the official Task Force benchmarks are released, this README will point
> to them as the authoritative source; until then, treat everything here as a
> **useful, well-documented starting point** rather than a settled standard.

## Why this should excite you

**If you're a researcher** — stop hand-rolling test cases. Grab a set of
spec-conformant instances with known topology, voltage levels, DER placement
and (for many cases) a reference solution, so you can benchmark *your* method
against a moving field on identical inputs. Every case is machine-readable
JSON, so wiring it into your own pipeline is trivial.

**If you're in industry** — these are derived from *real* utility feeders
(anonymised and openly licensed), not textbook toys. They exercise the
messy realities your tools will meet in the field: long rural SWER lines,
meshed MV/LV, neutral and grounding modelling, phase imbalance and high DER
penetration. Several sets permit **commercial use** (see licensing below).

**If you're building the ecosystem** — everything here is generated by an open,
scriptable pipeline, so contributed networks can be ingested, validated and
published the same way. Traceability is a first-class feature: every case
carries its source citation and licence. Good drafts here can become
candidates for the official Task Force library down the line.

## The BMOPFTools initiative

This repo is the companion **data** repository to
[**BMOPFTools.jl**](https://github.com/frederikgeth/BMOPFTools.jl) — the open
Julia toolkit that powers everything here. BMOPFTools:

- **parses** real OpenDSS networks into the clean BMOPF data model (via [PowerIO.jl](https://github.com/eigenergy/PowerIO.jl)),
- **validates** them against the BMOPF JSON schema,
- **analyses & reports** on topology, voltage levels, diversity and well-posedness, and
- **confirms** cases are solvable OPF instances before publication.

Every `*_report.md` and `*_tree.txt` you see next to a case was produced by
BMOPFTools. If you want to turn *your* OpenDSS feeder into a BMOPF benchmark,
that's the tool — and this repo shows you what good output looks like.

## What's in this repository

The data is organised in three tiers, from raw source material to ready-to-use
benchmarks:

### 1. `test/data/` — raw source networks
Openly-licensed source models: **OpenDSS** files (line codes, lines, loads, transformers,
`Master.dss`). This is the *starting material* — use it to develop your own
benchmarks, reproduce our conversions, or study realistic network structure.
Includes the ENWL four-wire LV variants (Kron-reduced and phase-to-neutral
forms), the scaled D-Suite LV networks, and 150 representative French MV/LV networks in Roseau JSON v5.

### 2. `output/` — power-flow (PF) cases in BMOPF JSON
The raw networks converted into clean, schema-conformant BMOPF JSON. These are
effectively **power-flow cases** — a faithful, validated digital twin of each
feeder — each accompanied by a human-readable `*_report.md` (component
inventory, voltage levels, connectivity, diversity metrics) and a `*_tree.txt`
topology view. Great if you want the network model without a specific OPF
problem baked in.

### 3. `benchmarks/` — curated OPF benchmark sets
The headline product: cases posed as **optimal power flow** problems, with DERs,
bounds, objectives and — where available — **reference solutions**.

- **`benchmarks/ENWLbenchmark/`** — ENWL feeders as 4-wire OPF instances
  (`original` and network-`reduced` variants), plus `opf_comparison.md`
  reporting solved objectives and timings in both SI and per-unit, so you can
  sanity-check your own solver against a known reference.
- **`benchmarks/ENWLsnapshots/`** — time-series *snapshots* of selected
  networks (e.g. `30bus`, `99bus`, `538bus` at line-to-ground / line-to-neutral
  variants) with per-timestep BMOPF cases, solved results (`*_result_si.json`,
  `*_result_pu.json`), daily/heatmap figures and a summary.

`scripts/FrenchPowerGrids/` contains the Python/Julia conversion and validation workflow for the French dataset.

`scripts/` contains the Julia pipeline (`generate_output.jl`,
`run_benchmark.jl`, …) that produced the OpenDSS-sourced cases — your reference for how
cases are generated and how to regenerate or extend them.

## How to use it

1. **Pick a case** — browse `benchmarks/` for OPF instances or `output/` for
   plain network models. Read the neighbouring `*_report.md` to understand size,
   voltage levels and DER content before you commit.
2. **Load the JSON** — the BMOPF model is plain nested JSON, so it loads in any
   language. In Julia, `BMOPFTools.jl` parses, validates and (via `to_pmd`)
   exports to PowerModelsDistribution.
3. **Check provenance & licence** — every case stamps its licence in
   `meta.license`, and every data directory carries a `License.md`/`license.md`
   with the exact terms and citation.
4. **Contribute back** — have an interesting real feeder? Run it through
   BMOPFTools and open a PR here.

## Representative French power-flow cases

[`test/data/FrenchPowerGrids/`](test/data/FrenchPowerGrids/) preserves the 150 source models and cluster weights;
[`output/FrenchPowerGrids/original/`](output/FrenchPowerGrids/original/) contains their BMOPF conversions with bus
longitude/latitude and explicit LV neutrals. The dataset-specific licenses retain Etalab Open Licence 2.0 attribution.
The conversion/validation scripts and tests have a separate MIT license.

All 150 cases converged in Tellegen's native multiconductor PF solver and passed independent electrical checks.
Five feeders also agree with fresh Roseau engine solves; the other 145 exceed the public trial license's 50-bus limit.
113 cases have voltages below their input bounds, and transformer loading constraints have a documented source/target
difference. These are PF models with reference solutions; future OPF curation needs its own feasibility checks.
See the [mapping and evidence](output/FrenchPowerGrids/README.md) and
[reproduction commands](scripts/FrenchPowerGrids/README.md).

## Feature tagging & discovery

Every curated benchmark is **feature-tagged** so you can pick and choose the
cases that match your study, and so the Task Force can see which algorithmic
behaviours the corpus exercises — and where the gaps are.

Tags are **derived, not hand-authored**: they come from the structured analysis
and the **best-known-solution profile** that
[BMOPFTools.jl](https://github.com/frederikgeth/BMOPFTools.jl) computes for each
case, mapped through a controlled vocabulary. We tag **three independent axes**
(following Geth et al., *EPSR* 235, 2024):

- **`model_tier`** (T1 → T∞) — *implementation effort*: how much of the data
  model you must support to consume the case (delta loads, transformers,
  voltage-dependent loads, control profiles, time series, …). Paper Table 6.
- **`benchmark_class`** (`core` / `watch` / `pathological`) — *well-posedness
  gate*: is this a clean, well-behaved real-world OPF, or does it carry an
  *artifactual* degeneracy (symmetry, rank deficiency, Kron ambiguity)? **`core`
  is the recommended set.** Pathological cases are kept and labelled — good for
  robustness testing, separated from the speed benchmarks. Paper Section 5.
- **`challenge`** (C1 → C3) — *genuine computational load* among clean cases,
  from the solution profile (degrees of freedom, binding set, iterations).

These are orthogonal: a case can be **`core` but C3** (a big, clean, richly-binding
network — the stress test you want) or **`pathological` but tiny** (a symmetric toy
with no unique solution — an artifact to fix). Catching pathologies fosters *robust*
algorithms; clean, large, binding cases foster *fast* ones — the Task Force wants
the latter. Each solved case also carries a `solution_profile`: degrees of freedom,
number of binding constraints, strict-complementarity (non-degeneracy), shadow
prices, and solver iterations.

Where to look:

| Artifact | What it is |
|---|---|
| [`docs/TAGGING.md`](docs/TAGGING.md) | The controlled vocabulary, all three axes, the solution-profile metrics, and every derivation rule. |
| [`benchmarks/tags_index.json`](benchmarks/tags_index.json) | Machine-readable tags for every curated case (schema: [`docs/tags_schema.json`](docs/tags_schema.json)). |
| [`benchmarks/INDEX.md`](benchmarks/INDEX.md) | Human-readable, sortable per-case table. |
| [`benchmarks/COVERAGE.md`](benchmarks/COVERAGE.md) | Feature-coverage matrix (features × dataset families) — the map of what's exercised and what's missing. |

Regenerate any time with `julia --project=scripts scripts/tag_cases.jl`. The
first cut covers the curated `benchmarks/` families; extending the same pipeline
to the full `output/` corpus is next.

Contributions, corrections and new source networks are welcome.
